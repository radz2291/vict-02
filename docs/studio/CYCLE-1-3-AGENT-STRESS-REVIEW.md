### Newly established findings and corrections to earlier uncertainty

**The input problem is an explicit adapter/description mismatch, not an unexplained lost edit.** `prepareAgentEdit` intentionally removes a new native input's value attribute and change interaction immediately after recipe insertion. This preserves the earlier design decision that independent form fields must not silently share the demo's message state. However, `agentContext.palette` still forwards the input recipe description, "Accessible input connected to message state". The model therefore receives a false description of what its add operation actually produces. This directly explains why it later asserted the email input was connected and skipped fixing it. Pure probes reproduce both the stripping and a successfully compiling, issue-free but unbound input. The current agent vocabulary cannot restore a native value reference/change interaction: bind targets component props, connect targets component outputs, and attributes accepts only scalars. All three attempted routes fail in the diagnostic. This is a concrete authoring capability/affordance gap; the deliberate independent-field rule itself must not be silently undone as a proposed fix.

**Same-batch add/connect is supported; the blanket explanation was wrong.** Adding a checkbox and connecting its compatible boolean output in the same transaction succeeds. Adding a button and connecting press to declared demo.submit in the same transaction also succeeds. A button press routed directly to boolean state fails even with an explicit correctly shaped literal expression: the compiler first requires non-void payload/state type equality. The authoritative comment documents this no-coercion boundary. This is a real existing contract limit, not proof of a broken batch dependency resolver and not authorization to change canonical semantics. A raw boolean in place of an expression separately fails the input schema. The assistant conflated these distinct failures and spent extra calls splitting transactions unnecessarily. The precise original first rejected payload remains unavailable, so these probes establish capabilities and distinctions, not an exact replay of that original call.

**The shared-state switch problem can compile successfully.** A generated switch with literal checked=false and checkedChange -> accepted passes the actual edit/compiler boundary. Connecting its output does not automatically create a matching checked reference, nor does it allocate an independent preference state. The observed terms/updates coupling therefore belongs in semantic design/completion review, not only schema validation. The current schema does not expose general scalar state-declaration authoring, while typed list properties have a specific automatic state path. Existing intended constraints need to be advertised honestly before the agent promises independent behavior.

**Seeded content really is appended to, rather than replaced.** Adding one custom Select item leaves the two recipe-created default items plus the new item. This reproduces the visible First option/Second option leftovers. Add semantics are not inherently invalid, but the model needs an explicit inventory and cleanup step when the requested result is an intentional custom example. The same initial review observed default overlay content left beside authored content; that specific overlay path was not separately replayed in this follow-up.

**Incomplete coverage is now measured against the actual authorable catalog.** The observed request asks for all available components in one intentional landing page. The current source uses26 distinct registered catalog definition IDs. The83 registered recipes expose78 distinct catalog definition IDs, leaving52 absent from this generated document. Context parts count separately; this is not52 missing top-level visual families or83 missing components. Absent examples include Tabs, Accordion, Progress, Calendar/date-range controls, dropdown/context/navigation menus, Toolbar and their parts. `coverage-inventory.json` records the complete missing-ID list and no unknown observed IDs. The existing hand-built `/showcase` coverage remains separate: its complete gallery does not make this agent-generated page complete.

**Nested buttons are confirmed in actual DOM, not just accessibility-tree interpretation.** `document.querySelectorAll('button button')` returns three nested pairs: Delete workspace, Filters and Share page. No control was activated. This is invalid interactive nesting and a concrete focus/event/accessibility concern; the exact behavioral failure across browsers remains untested. Four section headings also render as h1; this lower-priority semantic issue is recorded without claiming it caused the agent termination. The public Message/Copy repair is unrelated to these generated overlay compositions.

**Recovery instructions currently misdiagnose a deterministic size wall.** Reconnect agent only refreshes configuration/CSRF readiness; it does not reduce the full read context or its delivery size. A new turn injects the full context directly as initial input, but the model is instructed to invoke studio_screen_read; that same oversized tool result can fail again. Read failures remain in unresolvedTools until a successful read event occurs. Later successful writes clear only the edit tool's failure. Thus partial progress followed by terminal TOOL_FAILED is explained by the unresolved read even if the final writes succeed; it is not evidence that all12 applied edits rolled back. The code prioritizes this unresolved status over the underlying outcome code, leaving an exact step-limit versus ordinary finish attribution unavailable for this historical turn.

- The final outcome code can be replaced by the last edit failure or unresolved tool status. Combined with only eight recent progress entries and ephemeral full records, this prevents a conclusive historical call-by-call failure inventory. Missing observability is itself a finding; it must not be filled with speculative provider, storage or timeout diagnoses.
