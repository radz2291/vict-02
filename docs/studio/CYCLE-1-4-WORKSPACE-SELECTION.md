### Open findings and proposed resolutions

**SCR-01 — high priority: Layers does not follow a rendered repeated-row selection.** Designer passes no runtime scope to Layers. Layers therefore lists a template occurrence such as `repeat-review|field`, while Design renders `repeat-review|field|stable` and `...|stable#dup1`. Selecting the first rendered Input produces an exact canvas selection but zero selected Layer rows. `Layers.svelte` marks templates unavailable internally, yet the controlled selection-intent path accepts every visible row as a node occurrence. Source-only pruning also retains a syntactically valid stale row key; it cannot establish current rendered membership. Confirmed by the repeat/stale-row probes. Proposed: model source-template and live-occurrence rows explicitly; share the renderer's scoped outline where available, otherwise label Template/Not currently visible and locate its source without claiming an exact live row. Preserve selection across temporary visibility changes; do not silently retarget a row. Structure should explain when 2 occurrences map to 1 source card.

**SCR-02 — medium: scoped names become ambiguous in a set.** Two distinct `prop.title` declarations retain `Definition a` and `Definition b` in the graph. Single inspection shows Scope, but the multi-member list renders both as `Prop / Title`, with no scope. `WorkspaceSelectionDetails.identity()` describes occurrence contexts only, ignoring semantic-node scope. Single connection endpoints also use names without type/scope. Proposed: one shared identity presenter with quiet type, name and human scope/path when needed. Keep exact IDs in Technical information. The same presenter should serve node cards, relationship endpoints, member lists and agent context. Do not restore redundant type prefixes in names. Confirmed in `scopedNames` characterization evidence.

**SCR-03 — medium: single-node and edge/multiple panels have different geometry.** Single-node SourceDetails is a flex column with only its expanded section scrolling. Edge/multiple inspection is a block with the whole root scrolling. In actual mixed Relationships inspection, Technical information begins at y764.8, below the 668 CSS-pixel viewport; the single-node equivalent remains at y607.2. Header fonts/heights are already consistent (12px/18px, 36px), so broad typography changes are unnecessary. Proposed: reuse one exclusive-accordion frame, header spacing and section scrolling for empty, single node, single edge and mixed inspection. Source: `SourceDetails.svelte` versus `WorkspaceSelectionDetails.svelte`; measured in `panel-treatment.json`.

**SCR-04 — medium: relationship interaction and provenance depend on selection cardinality.** Single-node relationships are grouped clickable targets with directions and source-location tooltips. Edge/multiple Relationships renders static cards: no target navigation, no Ctrl-add intent, and no equivalent per-card origin/path access. The same connection thus becomes harder to follow after adding another selection. Proposed: reuse one relationship presenter and common selection intents, preserving plain-click inspect and Ctrl/Meta-add behavior with explicit From/To, role, origin and exact reference locations. Keep the selected set distinct from contextual related items. The characterization records 2 navigable single-node targets versus 4 static mixed cards; actual owner evidence confirms the treatment difference.

**SCR-05 — medium: partially selected connection points look unselected.** Selecting one of the Input's 2 Styles edges leaves its shared point `aria-pressed=false`, exactly as when none is selected. The row says Styles · 2; it does not say 1 of 2 is selected. Ctrl-click correctly adds the missing member, but feedback is incomplete. Proposed: derive none/partial/all from the explicit selected-edge set, show a quiet partial indicator/count, and expose the mixed state accessibly. Keep counts based on visible references and existing fixed-set group semantics. Actual counterexample: `partial-point.json`.

**SCR-06 — medium: Chat does not receive the shared selection set.** Designer still passes `singleOccurrence(workspaceSelection)` to the agent. Multiple nodes, any edge/mixed set, and single non-occurrence sources such as State are omitted. The chat selection label likewise falls back to None. A user can see two selected objects while the agent has no explicit selection reference for “these.” The UI probe confirms 2 canvas outlines with no Selected cue; source review confirms the context omission. Proposed: pass a bounded, passive typed selection summary from the same host owner, including exact occurrence/source/edge identities and human labels. Edit tools must retain their existing canonical, exact-base and single-target capability checks. No live provider turn was needed to establish this host-input gap.

**SCR-07 — lower priority: Overview usefulness varies sharply by type.** State and Input have meaningful facts and appropriate existing handoffs. Style, Token, Asset, Definition and Condition can show only Type while useful values/conditions/version information remain in Technical information. Multiple non-element sources usually compare only Type. Proposed: a small typed read-only facts provider per semantic family (style properties/condition, token value, asset kind, definition revision, boundary support/scope), with a consistent fallback. Keep editing in the current authoritative surfaces and never fabricate live values. The 26-presentation probe records each Overview; this is a usability gap, not missing selection identity.

**SCR-08 — medium: initial keyboard range selection has no anchor.** After focusing First in Layers without clicking, Shift+ArrowDown selects only Second. Further Shift movement still lacks a stable initial anchor because `rangeAnchor` is initialized only by a non-range selection gesture. Mouse click→Shift-click ranges work as previously tested. Proposed: establish the range anchor from the focused row when starting a keyboard range, retain it while extending/reversing, and keep Ctrl+Shift additive behavior. Confirmed by `keyboardRange` characterization evidence.
