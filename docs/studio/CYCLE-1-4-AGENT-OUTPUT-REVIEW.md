### AR-13 - Agent-authored Flow is a diagram viewer, below the owner's editor minimum (P1, confirmed contract gap)

The [authoring adapter](../../packages/ui-flow-svelte/src/authoring/FlowCanvas.svelte) sets `nodesDraggable={false}` and `nodesConnectable={false}` globally and also `draggable:false`, `connectable:false`, `deletable:false` on each projected node. Delete is disabled. Svelte Flow's installed default is `panOnDrag=true`; its node wrapper applies `nopan` only to draggable nodes. Consequently a drag originating on these non-draggable cards can pan the viewport, making every node appear to move together while individual graph coordinates remain fixed. These are distinct nodes, not a single authored group. Switching to Interact cannot enable a capability hard-disabled in the adapter.

The [descriptor](../../packages/ui-flow-svelte/src/authoring/descriptors.ts) explicitly promises read-only topology/positions and ephemeral pan/zoom/selection, with no workflow execution. Its node contract has only id/label/x/y, no child-content slots; its edge contract has id/source/target/label. Every Flow descriptor has `outputs:[]`. There is no exposed position-change, selection-change or connection-change output to bind into an authored application. Adding an unsupported `draggable` prop would not override these implementation flags.

Proposal: make reusable interactive graph presentation available through a versioned supported authoring contract, preserving the current read-only contract for existing consumers. Independent node movement, stable camera/layout, selection and inspection are baseline capabilities. Merely flipping a drag boolean would leave reactive updates, persistence and selected-item integration unresolved.

Source-kind icons intentionally describe source semantics; they are not a substitute catalogue of arbitrary application action/brand icons.

The [default element catalogue](../../packages/ui/src/semantic.ts) has img but no svg/path/group primitives, and no general authored icon/custom-icon component was found in the installed catalogues. Existing internal icon availability therefore does not mean the agent can discover/insert/recolour those icons in generated applications. The observed emoji-based menu, search and compose affordances are a visible consequence of limited exposed choices; this review does not claim that every emoji in every output was forced by the framework. Per owner preference, a professional UI icon should be the default choice for interface controls; emoji should not be the automatic substitute for a missing asset.

Proposal: expose a reusable Icon capability backed by a versioned icon registry. Offer an established supplied pack (the already-installed Lucide family is a candidate) plus application/workspace custom packs. Use stable pack/name/revision identities, searchable semantic tags/aliases and compact paginated discovery. Do not register every glyph as a separate giant component/tool schema or paste thousands of SVG paths into initial agent context. The agent should search/bundle relevant names, inspect exact metadata and insert by registry identity; unknown names should be validated and reported. Derive catalogue knowledge from the installed manifest, with clear available-versus-host-only status and licensing/provenance, rather than maintain a parallel handwritten icon list.

The authored contract should cover size, colour/currentColor, supported stroke/fill treatment, alignment and decorative versus meaningful accessible use. Custom icon import/registration should preserve viewBox/aspect ratio and intentional multicolour brand artwork; monochrome icons can follow theme colour. Use shared presentation foundations independent of ui-editor so generated applications do not depend on Studio's editor package merely to render an icon. Buttons, menus, drawer triggers, fields, node headers, tabs and status rows need actual icon slots/composition support: exposing an Icon node alone does not repair wrappers that own a fixed text-only trigger. Keep control labels and keyboard/touch behavior intact; icons must not become decorative replacements for functional controls.

### AR-29 - Reusable custom vector graphics and brand assets lack a first-class authoring workflow (P2, owner-requested capability gap)

The basic img element can reference a supplied browser-loadable SVG URL as an image, subject to the existing image/source path. That is different from an imported, managed custom icon or an editable inline vector composition; no new SVG loading test is claimed here. The current asset workflow gaps in AR-22 still apply. CSS shapes/gradients are possible, but no registered general SVG/vector composition surface was found for authoring paths/shapes/groups through the agent. Internal SVG rendering in Studio does not establish that capability.

Proposal: support both reusable vector assets (logos, brand marks, decorative illustrations/patterns) and an extensible declarative vector composition surface. A useful initial scope includes viewBox, paths, rectangles/circles/lines, grouping/transforms and explicit fill/stroke/opacity, with gradients/clips/masks where supported by the actual implementation. Define sizing, cropping, aspect ratio, layering and responsive behavior. Separate editable geometry from referenced immutable assets, retain reusable asset identities and make updates affect intended instances consistently. Preserve authored brand colours and offer intentional themeable parts instead of recolouring every imported graphic automatically.

Integrate custom-vector import with the explicit media/asset pipeline: bounded validated inert SVG/geometry data or stable managed references, not arbitrary script-bearing markup or generated executable snippets. Namespace internal gradient/clip/mask IDs per occurrence to avoid collisions across repeated graphics and multiple documents. Keep source/history/save/reopen and standalone rendering coherent; asset references must resolve after reopening, not depend on a temporary local/blob URL. Advanced authoring features should be advertised only when implemented and tested.

Proposed acceptance for both findings: agent-authored examples using supplied icons and a custom icon/logo; meaningful icon controls in navigation/forms/nodes; decorative graphics with correct accessibility; monochrome theme inheritance and preserved multicolour branding; different sizes/zoom/mobile widths; alignment with text; repeated instances with gradients/clips; unknown/missing asset handling; and save/reopen/Run portability. Inspect actual rendered output and unchanged interaction behavior. These requirements should improve creative range across projects through reusable capabilities, rather than prescribe one application's icon choices or a fixed visual template. AR-28/29 remain **OPEN / REPORT ONLY**, linked to AR-22 media and AR-13-15 rich-node targets.

## Holistic resolution proposal - not authorized for implementation

A general workflow should be Find target -> Inspect effective capabilities/context -> Prepare valid change -> Apply atomically -> Verify affected surfaces/states -> Report outcome or next required action.
