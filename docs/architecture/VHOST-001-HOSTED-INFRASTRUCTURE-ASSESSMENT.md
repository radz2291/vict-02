# VHOST-001 — VICT hosted infrastructure assessment

22 November 2026 · Research candidate for Radzi's review

## Decision

| Package | Recommended disposition | Responsibility |
| --- | --- | --- |
| @victframework/store-postgres | **REPAIR** | Keep the provider-neutral PostgreSQL implementation of VICT operational ports. Replace namespace-wide hot-path snapshot access with indexed, bounded reads and atomic writes at the record or aggregate boundary. Preserve ports, identities, ordering, retention rules and transactional fences. |
| @victframework/hosted | **KEEP** | Keep the optional bounded Fetch request adapter for short, observable units of work. Qualify its composition and share proven transport primitives where appropriate. Quellight should qualify the store upgrade independently of any adoption of this handler. |

Start the specification with an indexed relational operational store and a shared conformance matrix. Preserve the snapshot adapter as a bounded legacy baseline and migration source. Fit long or unattended execution around durable state and existing runtime policy, using the chosen host's wake mechanism or a worker as appropriate. Keep VICT Core, application delivery, Mastra storage and Supabase-specific integration at their existing boundaries. A separate Supabase package remains deferred pending a concrete capability that the PostgreSQL adapter and ordinary app integrations cannot supply. ## 2. Store mechanics and failure boundaries

The public root exports createPostgresStores and PostgresCoordinationStore, with types PostgresStoresOptions, PostgresOperationalPorts and PostgresStoreSet. The store supplies VICT's execution, retry/wait orchestration, activation and control, agent/actor/governance, turn/cancel, invocation and stream ledger ports. The composition exposes coordination, leased and unleased access, the coordination pool and transaction surfaces, and close. Treat raw SQL and unleased ports as trusted infrastructure surfaces. Namespace is a persistence and locking boundary. Product actor checks and DB privilege enforcement govern its use.

| Mechanism at 1b11d4a | Finding and implication |
| --- | --- |
| packages/store-postgres/src/index.ts:1–4 and adapter.ts:38–49,100–166,250–290,908–914 | Fresh reference engines hydrate the state after fetching the single namespace snapshot with SELECT FOR UPDATE. Reads of a turn, flag, actor or stream range still fetch and hydrate the bundle. A mutating port persists the full serialized JSONB snapshot within the transaction. Stream cursor semantics reduce the application response, while the snapshot transfer remains. A hot namespace serializes lock-taking operations across its actors and rooms. A separate namespace can reduce contention but requires a defined ownership/routing model and preserves per-namespace amplification. |
| packages/store-postgres/src/driver.ts:98–174,198–302 | The bounded driver uses parameterized queries, one checked-out client per transaction, local statement/lock/idle-transaction limits and verified TLS by default. Defaults include 1 pool connection (allowed 1–10), 5 s connect, 10 s statement, 5 s lock, 8 MiB snapshot, 100,000 state nodes, 10,000 scopes and 20,000 effect receipts. These are limits and error boundaries. They establish no throughput target. Even migrate false verifies metadata and attempts a namespace INSERT ON CONFLICT DO NOTHING at initialization. Qualify privilege, connection and startup effects separately. A connection failure around COMMIT may hide a committed operation. Read durable receipts before resuming. |
| packages/store-postgres/src/coordination.ts:98–120,122–200,203–266,281–357 | SQL-backed namespace/scope serialization uses the DB clock. New ownership increments a fence. Renewal preserves that generation; stale release leaves the successor intact. Deletion sets sticky intent and preempts ordinary work. withFence checks actor, owner, generation, purpose, deletion and expiry before and after the callback on the same transaction connection. Trusted code must avoid bypass through unleased ports or direct writes. Keep network and provider waits outside SQL transactions. |
| packages/store-postgres/src/coordination.ts:281–357 | Effect receipts reserve an uncertain outcome before dispatch, bind identity and argument digest, reject conflicts and resolve through observed/reconciled outcomes. Matching settled retry can replay; matching unresolved retry remains uncertain. This safeguards governed use and recovery. External effects require a trusted idempotency key or a status/reconciliation channel for their own system. |
| packages/store-postgres/src/driver.ts:198–245 and adapter.ts:250–290 | Under contention, a per-pool cap can shift time into client acquisition; pooler limits can shift it again into server admission. Row-lock wait, SQL execution, transport, JSON decode/hydration and response projection all need separate instrumentation. A higher pool limit alone cannot parallelize the same lock. Read-only query/index tuning alone cannot remove transfers of the selected whole column. |

The architecture preserves atomic in-namespace reference-model mutations and store-backed replay. Its maturity is bounded qualification. Growth increases per-call payload and hydration work and single-row contention limits throughput. These mechanisms also expose possible WAL, TOAST, vacuum, and timeout pressure under writes. Those are testable hypotheses. The current independent evidence did not size the adapter under sustained traffic. ## 3. Hosted request lifecycle and overlap

- **Shared helper.** The root exports readHostedEnvironment, HostedConfigurationError, createHostedRequestHandler, HostedRequestRefusal and readHostedJson plus composition types. The package also exposes the Vercel profile through its subpath. Environment parsing bounds configuration, including privileged TLS inputs. The current reference profile describes a 60 s function envelope split into 45 s work, 10 s settlement and 5 s response reserve. Its configuration generator sets a function duration and offers an opt-in cron entry. The application binds deployed routes and selects its platform/runtime. [Vercel duration](https://vercel.com/docs/functions/limitations) · [Vercel waitUntil and deadlines](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package)
- **Request contract.** Authenticate before bounded parse, then open a trusted actor/lease/run/activation-bound session. Work has an abort signal and a cooperative deadline. Settlement releases the lease, obtains a fresh durable observation, validates actor/run/activation and positive revision, then disposes before success. Waiting returns 202 with continuation identity, blocked returns 409 with inspection guidance, terminal durable observations return 200 with truthful status, and missing, running, mismatched, uncertain, or unconfirmed settlement returns 503. A deadline race can return with cleanup pending. An ignored signal or abrupt host termination can leave work or effects requiring durable recovery. A late-open cleanup is best-effort and lease expiry remains relevant.
- **Authority and coherence.** The callback owns authentication, scope binding, exact activation restoration, runtime interpretation, continuation comparison, and complete effect observation. The helper can validate the returned binding and revision shape. A later owner may progress after release, and application observers using multiple queries need a coherence contract for reported revision and effect status. A public response should avoid exposing internal payloads indiscriminately. Test the same candidate around deadline, disconnect, acquisition, COMMIT, cleanup and redeploy.
- **Division of work.** @victframework/server owns authenticated command/operator HTTP routing, write envelopes, API/SSE cursors and Node HTTP lifetime. Application hosting owns routes, sessions and rendered app serving. Hosted's reusable value is the bounded Fetch execution and settlement protocol, independent of product rendering and Node server boot. Compare and, where ABI permits, share proven parsing, actor-envelope or cursor primitives. Preserve both entry points until overlap has a call-site and migration inventory. VICT Runtime and control own capability, actor, activation, effects and durable semantics.

Framework evidence at 1b11d4a5f4298310c7ab16e0808b8bfbed551ee5: packages/hosted/src/index.ts:1–12, environment.ts:44–105, request.ts:43–67,134–431 and vercel.ts:7–74. ## 4. Egress evidence and benchmark design

Quellight's investigation records **32,137 full-snapshot query calls** and a **~1.56 MB snapshot at inspection**. The **22.33 GB** Supabase dashboard observation aggregates **three projects**. The sampled size lacks a historical distribution, and query calls lack byte attribution and a matched billing window. The arithmetic 32,137 × 1.56 MB ≈ 50.1 GB illustrates the constant-size assumption only. It is neither a project estimate nor a way to reconcile the dashboard. The measurable fact is repeated namespace payload retrieval on the hot path. The cost and latency share remain open. ### Measurement protocol and cross-cutting gates

1. **Baselines.** Run the pinned snapshot adapter and candidate using the same synthetic seed. Record Node, package digests, hardware, PostgreSQL, pool mode, TLS, retention, actor/room cardinalities, and dataset sizes. Use initial operational fixtures near 0.10, 1.56 and 7.5 MB and a repeatable beyond-limit case to record the RC's controlled failure. Grow indexed history independently up to the agreed stress tier. Exercise one namespace, multiple namespaces and hot keys. Use seeded traces at 0.5×, 1× and 2× offered target rates, three 2-minute warmups plus 10-minute steady samples per cell, and a 60-minute target-load soak for shortlisted configurations. Keep the raw aggregate results and failed runs.
2. **Traffic and cost.** Count per-port calls, SQL reads and writes, returned rows and bytes, normalized query calls, database-to-client wire bytes, client-to-database bytes, WAL bytes/action, and pooler and provider metrics where available. Report per visible reply, per turn-minute, per committed effect and per 1,000 workload operations. Driver payload measurements and wire/provider metrics need different labels. Estimate monthly cost only from matched project windows and the then-applicable provider terms. First candidate goal is zero full-snapshot SELECTs/UPDATEs on indexed point and range paths, ≥80% fewer DB response bytes per representative Quellight turn versus a matched pinned synthetic trace, and ≤10% point-read bytes growth as unrelated history grows 10×. [PostgreSQL statement metrics](https://www.postgresql.org/docs/current/pgstatstatements.html)
3. **Latency and admission.** Report p50/p95/p99 and error rates by route and port. Break out pool acquisition, lock wait, SQL, decode/hydration, wire/response, time to first durable text, first visible text, cancel acknowledgement and outcome, and queue age. Separate warm/cold connections and provider latency. Count app pools, connections per instance, pooler client/backend peaks, waiters, timeouts, CPU and RSS. Proposed targets at 1× are <0.1% unexpected errors, p95 lock wait ≤25 ms, and peak connections ≤70% of the agreed usable pooler/server budget across live, wake and migration traffic. Expected refusal/uncertainty from scripted faults gets a separate counter. At 2× require bounded admission and documented saturation, with no correctness regression. [node-postgres Pool counters](https://node-postgres.com/apis/pool) · [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres)
4. **Correctness and isolation.** Run current store/runtime/hosted conformance on the installed dependency closure. Compare replay, revision, approval, ordering, deduplication, paginated stream cursor, deletion and retention across both adapters. Interleave unrelated and competing scope claims, check stale fences before/after callback, prove no post-revocation side effects under the agreed policy, and assert zero cross-actor or cross-namespace data leakage. Test restricted runtime grants, verify-only startup, TLS hostname and CA, payload/body/response bounds, and sanitized logs with synthetic canaries. Compare operational backup/recovery and index/migration overhead for maintainability.
5. **Failure and recovery.** Stage lost response, timed-out lock, aborted or late callback, process death before effect dispatch and after dispatch before receipt, ambiguous COMMIT, failed cleanup, host redeploy, cron interruption and DB restart/failover. Observe unknown effects without automatic reissue. Verify ordered cursor replay, one publication after checkpoint, successor fencing, and restore/rollback with counts plus identity/digest sentinels. Proposed recovery gate is zero loss for committed data in ordinary process/redeploy faults and documented RPO/RTO for database disaster recovery from a timed restore test. Set an explicit owner-approved RPO/RTO before production approval.

## 5. Architecture options and specification sequence

| Option | Benefit | Tradeoff and compatibility |
| --- | --- | --- |
| Keep the snapshot with larger caps, faster pooling, less polling or co-location | Quick mitigation and a baseline for small bounded workloads. Coalescing calls may reduce repeated work. | Lock and payload scale with a namespace. Higher caps move the cliff. Polling changes affect Stop and reconnect behavior. Co-location can change billing/latency while retaining queries and hydration. |
| Add indexed hot read projections beside the snapshot | Provides a reversible, smaller first slice. Useful when benchmark data identifies one dominant query path. | Write amplification and the namespace lock survive. Derived views need a transactional version, drift checks and explicit stale-read rules. Avoid asynchronous read models for authorization, Stop or effect truth. |
| Replace the snapshot with indexed operational records inside store-postgres **(recommended)** | Port-shaped bounded reads, granular changes and narrower contention. Separate historical retention from the active path. | More migration/index/locking and maintenance work. Preserve old export/import semantics and scale-test the most contended transaction before broad port conversion. |
| Absorb hosted into server, or drop the helper | A possible simplification if independent adoption and closure analysis shows all useful behavior has a natural owner elsewhere. | Node HTTP and Fetch functions have different lifetimes and consumers. Absorption changes an installed entry point and can increase coupling. Keep the bounded helper while reviewing genuinely common primitives. |
| Put hosted state in a Supabase-specific service or move every workload to a queue | Provider services can be evaluated for a demonstrable scheduling, auth or delivery capability. Workers offer deadlines suitable for long or unattended execution. | Provider coupling or queue ownership would expand the spec. Treat the queue as a wake mechanism, with durable authoritative state and deduplication in VICT/product records. Serverless, worker and no-hosted profiles should use the same semantics. |

1. **Freeze the compatible surface.** Inventory every operational read/write and transaction across runtime, control, Mastra and app glue. Classify consistency needs and catalog ordering, cursors, error codes, identity, serialization and atomically maintained relationships. Keep the neutral contract and reference conformance as the oracle. Document lock and transaction order, allowed SQL callback behavior, effect uncertainty, clock and retention policies. Confirm which public DB/driver methods are actually consumed before carving down their surface.
2. **Specify indexed storage.** Define tenant/namespace boundaries, point keys and cursor indexes, compare-and-set guards, atomic grouped mutations and archive rules. Candidate hot paths include actor, exact activation, turn and cancel intent, stream events keyed by stream identity and sequence, invocations, governance and effect receipts. Choose consistent views for effect-plus-run observation. Keep legacy and candidate schemas independently openable and provide migration readers, a verifier and a reversible cutover strategy. Require least-privilege and bounded pool admission under each supported topology.
3. **Specify hosting by lifetime.** Keep the Fetch helper for bounded request work and clear settlement within the host budget. Specify durable activation/receipt-based resume and transport-neutral wake/worker integration for longer work. Check compatibility against Node server routing, resumable SSE and Quellight's product poll/wake paths. Align shared transport behavior only where it keeps caller contracts stable. Distinguish an accepted job, durable terminal result and externally uncertain effect.
4. **Gate A — Independently verify reusable packages.** Fresh verifier receives exact source commit, artifact digests, clean consumer locks, old and target schema fixtures, compatibility matrix, and raw benchmark/fault outputs. Verify neutral workflow and AI consumers, cross-actor isolation, replay, restart, expiry, backup/restore, pool limits and dependency containment. Require explicit disposition for each supported profile and publish the independent verdict. This research and the historical bounded F4 verdict do not satisfy Gate A for a modernized candidate.
5. **Gate B — Migrate Quellight and validate production.** Gate A qualifies the reusable candidate. Quellight then needs separately authorized application packaging, migration rehearsal, protected Preview, production cutover and project-specific acceptance. Record the production rollout and reviewer verdict separately.

## 6. Quellight qualification and rollback plan

1. **Acquire authorization and establish pre-change evidence.** Pin the exact app/deployment inputs and both current and candidate archive closures. Keep the app's C12 runtime/Mastra hashes unless qualification requires advancing them. Verify the lock, type declarations, installed file tree and server imports using the pinned toolchain. Preserve the tested rendering/UI baseline. Establish project-specific egress windows, routes and function timing, DB query counts, bytes, pool/lock waits, error and uncertainty rates, and usage denominators before a deploy. Instrument aggregate counters and redact content, identities in logs and credentials. Obtain an owner-approved maintenance window, recovery budget and abort thresholds.
2. **Rehearse on isolated fixtures.** Inventory snapshots, activation and actor state, runs, turns, cancel intents, invocation/effect receipts, streams, lease generations, tombstones, and any other payload from the migration version. The SQL coordination state must move with or be deliberately fenced against the snapshot epoch. Map exact keys and revision/sequence ordering, including unknown outcomes and retention. Verify deterministic count/digest comparisons and sampled equivalence through public ports, plus relationships to product turns/projections/chunks and C12 memory references. Restore the old backup on a disposable target and time both forward and reverse rehearsals. Keep product and Mastra memory schemas under their existing owners.
3. **Validate a protected Preview.** Run two-client desktop/mobile sign-in and owner revocation checks, two overlapping turns with dedicated leases, start retry after response loss, Stop, reconnect, transcript projection, export and deletion. Exercise the real hosted timing/settlement boundary with separately authorized synthetic provider access if required.
