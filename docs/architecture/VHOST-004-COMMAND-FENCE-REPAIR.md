## Implementation

The version-3 disposable schema adds an append-only table keyed by namespace and SHA-256 digest of the supplied fence’s exact UTF-16 bytes. Every new pending claim and every successful takeover reserves its token in the same PostgreSQL transaction as the receipt write after the existing receipt locks. A unique insert arbitrates even concurrent claims for different keys. The fixture keeps committed reservations through release, completion and writer epoch changes. A duplicate or absent initial token returns `VICT_IDEMPOTENCY_FENCE_CONFLICT` before creating a receipt. A hash collision fails closed. The normal takeover uses the reference-derived token. If the per-receipt attempt counter resets after release and the reference token recurs, takeover reserves a new random token and returns it to the caller. The released token stays retired. [Implementation](vhost-003-candidate/indexed-receipts.mjs) · [Schema](vhost-003-candidate/receipts-schema.sql)

Replaying a still-present receipt skips token reservation and returns the existing result. Settlement and release continue to use the pinned Runtime’s exact current-token check. The strict initial-claim rule applies to pending receipts because those carry settlement authority. The test fixture does not run standalone expiry cleanup or purge the fence history. Retention and restoration have to preserve its guarantee before a supported package can serve. The version-3 harness creates its schema from scratch. Version-2 data lacks a complete historical token set, so an upgrade from that fixture cannot infer that every old fence was retired.

## Verification

PostgreSQL 18.6 reproduced legacy token reuse. The repaired store survived pool close and reopen, refused a fresh claim with either retired token or a missing token, and admitted a fresh token with the same owner, key and initial attempt count. Both retired tokens failed against all three mutation ports. The persisted receipt was byte-identical across all six refusals. The fresh token completed successfully. A repeated expired takeover whose reference token had already been used received a new token, and the previous takeover token stayed fenced.

Two concurrent claims on different keys presented the same unused token. Exactly one acquired it. A separately injected pre-COMMIT failure rolled back both the receipt and its token reservation. The same token then acquired successfully on retry. The pinned four C12 paired transactions and all 113 new-family and 79 prior differential calls passed alongside the prior namespace, epoch, concurrency, rollback and ambiguous-COMMIT checks. This run was correctness-only. The earlier matched performance measurements describe version 2. ## Pinned callers and integration limits

The pinned dispatcher uses one owner per service instance. Its ordinary command, confirmed command and confirmation-prepare paths each derive a new claim’s token from that owner, command identity and `attempts: 1`. The legacy `claimReceipt` result is only `claimed` or `exists`; it cannot hand a replacement token to an unchanged caller. Disposable dispatcher tests exercise the original retryable release path. The legacy instance reproduces same-token reclaim. The strict candidate rejects that retry before a second domain invocation. A newly composed caller with a fresh owner identity acquires and settles, then replays from the durable result without invoking the domain again. This qualification is a fixture result. An approved package path needs a fresh acquisition identity in the actual caller or a revised token-returning claim contract. The public ports, legacy package and Quellight checkout were untouched.

VHOST-004 is still in Review. Work required owner authority to reopen it, so the isolated repair is submitted under the linked follow-up. The simultaneous different-command key-reuse check and coordination text-key compatibility remain Gate A items. D5's atomic prepared-digest rule remains with the authorized control-plane work.
